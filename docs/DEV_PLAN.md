## 开工前确认的技术栈

产品形态按规格第 17 节：微信小程序，375 逻辑像素，系统胶囊与安全区单独处理。视觉以第 17.2 节色板和字号为准，不再另开一套视觉方向。

| 方案 | 组成 | 适合 |
|---|---|---|
| A（推荐） | Taro + React + TypeScript 小程序；Go（Gin）规则 API；PostgreSQL；OpenAPI `/v2` | 规则、修订、预约留位放在一个有类型的服务里。附录 Python 只作对照测试。小程序类型由 OpenAPI 生成。 |
| B | 同上，数据库改为 MySQL 8 | 托管环境只有 MySQL，或团队只运维 MySQL 时使用。JSON 以 Go 校验为主，少做库内查询。 |
| C | 微信原生小程序；其余同 A | 不想引入 Taro 时使用。后端选择不变。 |

推荐按 **方案 A** 拆下面的任务。M0 的 JSON 配置与 M1 的验收用例不依赖小程序框架。

契约顺序：先冻结 OpenAPI 和错误码，再写 API，再让小程序按契约接。页面里不复制一套分支或计分判断。

## M1 规则引擎

规则放在 `apps/api/internal/rules`，API 只编排持久化和权限。每条验收对应用例，输入是已校验的答案表。库存、幂等和协议确认用显式 SQL 事务，不把这类写入交给 ORM 自动拼装。

- [ ] **T1.1 量表。** `score = 25 × (有效题反向处理后的均值 − 1)`。`unknown` 与未答不进均值；Likert 3 进均值。缺覆盖或缺少要求的正反向题时该轴为 null。隐藏题不加入五轴均值。验收 V006–V009、V011。
- [ ] **T1.2 分支计划。** 基础 60 题全部处理完才由服务端计算触发。优先级 C → S → N → T → P。第一阶段四题一段，处理完才决定第二阶段。P 线按轴两题一段。用户可暂缓非必要分支；已出现的基础 `no` 立即生效。改答案后重算，不再触发的题标 `superseded`。未激活题提交返回 `INACTIVE_QUESTION`。验收 V002–V004、V012、V014。
- [ ] **T1.3 坦奶。** 唯一 `subtype`，`group` 与 `code` 由它派生。快速判定、C 线补证、H005 父类约束 H008。非法父子组合拒绝。无法确定时 `pending`，不默认奶。新手有效作答 `basis=imagined`。验收 V005、V013、V015–V021、V023、V068。
- [ ] **T1.4 五字母、雷达、叙事。** `>50` / `<50` 取字母，40–60 为 flexible，等于 50 时基础字母为空。前四轴可在 P 题同向时给出 `context_reference`，基础分仍保持 50，不回写匹配分。movement 临界保持待了解。雷达缺轴断开，不补 0。验收 V007、V008、V010、V024。
- [ ] **T1.5 剧情情绪。** `story_emotion` 与 `story_tears` 独立。矛盾时 `context_varies`。不进入五轴、六星、坦奶和双人五轴分。验收 V069–V073。
- [ ] **T1.6 报告组装。** 报告含五轴与覆盖、字母、16 主角色、K/R、六星、剧情情绪、叙事、坦奶、情境标签、边界默认、规则键、未完成分支、版本与时间。主报告最多 2 条优势、2 条风险、3 个动作。无证据不编造缺点。解释可回溯到题目，只给本人看。
- [ ] **T1.7 会话修订。** 保存 `seed`、`base_order`、`branch_plan`、`trigger_evidence`、`dependency_hash`、`question_version`。基础题分段混排规则按第 6.5 节。同一题重答不增加题量。H005 变化清空 H008。
- [ ] **T1.8 Oracle。** 用规格附录的 Python 对同一批 fixture 对照计分、分支、坦奶和候选。不一致时以规格正文为准，并记下附录差异。

## M2 测评小程序

- [ ] **T2.1 测评 API。** `POST /v2/assessments`、`PATCH .../answers`、`GET .../plan`、`POST .../submit`。`expected_revision` 冲突返回 `REVISION_CONFLICT`。相同修订的提交幂等。
- [ ] **T2.2 开场资料。** `gender`、`age_band`、可选精确年龄、外观、年龄外观、经历、昵称。无默认性别。年龄矛盾时让本人确认。改年龄或性别不改变人格、坦奶和匹配分。外观不能反推性别。验收 V022、V067。
- [ ] **T2.3 答题流。** 首页、资料、基础单题、分支说明、补充题、答卷检查。选择后不自动跳题。`unknown` 位置固定。基础进度显示 `n/60`，补充段显示当前段进度，不从 60/60 跳成 60/100。离线与重启恢复顺序和答案。验收 V064。
- [ ] **T2.4 结果页。** 代码、坦奶徽章、一句话、五轴、六星文字数值、剧情情感反应、叙事与建议。人物区用剪影占位。分享卡默认不展示落泪；预览后才生成只读快照。换装只改外观，不重算人格。
- [ ] **T2.5 图鉴。** 16 主角色与 K/R 文案、坦奶叠层说明、附录候选方向。图鉴标明“类型方向推演”，不冒充用户报告。
- [ ] **T2.6 视觉与状态。** 使用第 17.2 节色值、字号、44px 触控。待确认同时用文字、图标和浅底。动效可关闭。覆盖草稿、部分完成、临界、缺失、想象作答。

## M3 图鉴配对与熟人邀请

- [ ] **T3.1 类型候选。** 个人基础五轴对 32 原型。同频 3、互补最多 2、需沟通最多 3。缺轴、有轴等于 50、或至少 3 轴 flexible 时不做个人排行。验收 V028。
- [ ] **T3.2 双人同频。** `sim = 100 − abs(x − y)`，按场景权重和 coverage。演绎缺 interaction/focus，或黑追缺 intensity/movement，或 coverage < 0.8 时分数为 null。交换双方后分数与冲突对称。验收 V025–V027。
- [ ] **T3.3 协议与坦奶方向。** 明确拒绝优先于高分。坦奶矩阵只给支持方向，不自动分配陪同。剧情情绪只在双方授权时出现，不加减匹配分。验收 V029–V032、V074。
- [ ] **T3.4 邀请。** scope 逐项授权。剧情情绪默认私人。邀请默认 7 天，服务端校验过期和撤销。拒绝披露时只显示“尚待本人确认”。验收 V049、V050。
- [ ] **T3.5 找搭子页。** P0 只有类型参考和熟人邀请。发现入口显示未开放，不用假用户列表。

## M4 主题录入与单人适配

- [ ] **T4.1 人工发布。** 内部录入 ThemeVersion：五轴档位与证据、玩法原子、角色路线任务、陪同容量、内容提醒、`emotional_tone`。关键字段需确认后才可发布。发布版不可变。AI 提取不进入 P0。
- [ ] **T4.2 暴露与硬边界。** `Exposure = 全员任务 ∪ 角色任务 ∪ 路线任务`。`no` 遇必做为 conflict；`avoid` 与 unknown 为待确认。贴脸与身体接触分开。题材 dislike 是软偏好，内容 `no` 是硬边界。催泪兴趣用本人的 `moving_story_interest`，不从 E 题推断。验收 V033–V040、V075–V077。
- [ ] **T4.3 软分。** 硬条件之后才算 `theme_similarity`。mixed 没有 alpha 时分场景展示，不合成一个分。冲突时分数不作主结论。验收 V038、V039。
- [ ] **T4.4 主题页。** 列表与详情分开“类型建议”和“个人适配”。关键资料未核实不显示已适配。

## M5 队伍、本场表单与求解

- [ ] **T5.1 队伍。** owner、成员、容量、可见性、城市、时间、预算、场景意向、修订号。P0 容量建议 2–8。加入需本人同意共享字段。队长不能代答、代接受接触或代确认陪同。离队后撤销对该成员私人档案的后续读取。验收 V047、V066。
- [ ] **T5.2 本场表单。** 与人格测试分开。旧答案只预填，绑定 `member_condition_revision`。把 `no` 改为 accept 必须本人主动确认。
- [ ] **T5.3 协议。** 相同 value、scope、`dependency_hash` 下全员确认才 `accepted`。改核心字段后原确认作废。验收 V048、V053。
- [ ] **T5.4 求解器。** 先筛个人×角色可行边，再搜整体分配。角色方案与陪同方案必须同时可行。同一时间同一人不能在两个房间。目标顺序：最大化全队最低个人软分，再最大化均值，再减少不符合角色偏好的次数，再按成员 ID 与角色 ID 稳定选取。超时返回 `calculation_incomplete`。任一成员的明确拒绝不被多数覆盖。验收 V041–V046。
- [ ] **T5.5 队伍适配页。** 展示每人安排、冲突、支持任务和原因码。不公开他人私人拒绝原因。无主题时只给偏好相近、待约定或资料不足，不显示已适合预订。

## M6 预约申请

- [ ] **T6.1 申请状态。** `draft → submitted → merchant_review`。P0 无库存系统时停在待商家确认，不承诺实时空位，不显示已支付。验收 V059。
- [ ] **T6.2 就绪条件。** `BookingReadiness` 与人格报告、队伍状态分开。成员、快照、硬冲突、陪同、场次、条款、资格任一项变化都使相关确认失效。
- [ ] **T6.3 商家最小信息。** 人数、日期、选定方案、必要玩法要求、需确认的支持安排、已授权联系人。不发送原始答卷、D/F/E、精确年龄和私人拒绝原因。
- [ ] **T6.4 幂等。** 创建申请使用幂等键。相同 payload 返回同一申请；不同 payload 返回冲突。验收 V055、V056 的申请段。

## M7 商家试点（P0 验收后）

- [ ] **T7.1 工作台。** 门店、主题版本、场次、待确认安排、预约、反馈。员工权限按门店隔离。验收 V051。
- [ ] **T7.2 发布审核。** 商家逐项确认，平台审核映射。外部文案里的指令不改变校验。验收 V033、V052。
- [ ] **T7.3 报价与留位。** `offered` 带报价版本、条款、`hold_expires_at`、主题快照。改报价生成新 offer。确认在事务内检查快照、确认、库存、角色容量和幂等。两队争最后名额只有一个成功。验收 V054、V057、V060、V061。
- [ ] **T7.4 支付位。** 状态机预留 `not_required`。未接入支付前不出现已支付。支付成功但库存失败走异常，不显示预约确认。本阶段不接真实支付渠道。验收 V058、V059。

## 横切事项

每个里程碑都要带上，不单独堆到最后：

- 私人资源校验 owner 或有效 scope。分享用脱敏快照，不直连私人报告。
- 日志不写全量原始答案、精确年龄、联系方式、受限剧情。
- 算法结果带 `rules_version`、输入 hash、证据。已分享结果和已确认订单不因规则升级被静默重算。
- 小程序未开放能力用明确空状态，不用假数据冒充。
